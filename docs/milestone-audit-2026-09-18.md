# VeritasMed：GitHub 展示里程碑审查

审查日期：2026-09-18。对象：当前本地工作区，基于 `main` / `431e2a6`，包含用户已有未提交修改。本文是现状审查与建议验收范围，不表示已经完成发布或修复。

## 结论

项目已具备完整的研究原型结构，足以体现文献处理、检索、Agent 编排、前后端集成和评估能力。当前主要缺口是工程收敛：首次运行、功能承诺与真实行为一致、评估可追溯，以及便于访客理解的演示材料。

建议首个展示版本命名为 **v0.1.0 — Evidence-grounded Literature QA Demo**。定位为以影像相关文献为主要语料的医学文献检索与问答研究演示。证据一致性自检属于模型辅助检查，不应宣传为临床正确性保证。

优先完成一个小而可靠的展示闭环：问题 → 检索证据 → 回答及引用 → 原文定位 → 自检结果 → 无证据时明确说明。

## 3. 发布阻断项

### P0-A：评估成绩与定义必须统一

README 首页将 `0.818` 标为 50 题成绩，并列出 P2/P3 Recall@5、MRR 均为 100% / 1.000。当前评估文件不支持这种统一表述。

| 结果文件 | 实际含义 |
|---|---|
| `agent_eval_hard_v4.json` | 39 题 hard 历史结果，复算 composite = 0.8179487 |
| `agent_eval_v2_strict.json` | 标称尝试 50 题，49 题有评分、1 题失败；成功题 composite = 0.6711551 |
| 同一 strict 结果，失败题按零计入 | composite = 0.657732；这是本轮重算口径，不是新增模型评测 |
| strict 失败项 | Q031：`'dict' object has no attribute 'strip'`；需重现后定位，不能据历史错误推定当前根因 |
| strict 成功题平均 judge 分数 | faithfulness 0.9633、relevance 0.7096、correctness 0.3406 |

这些都是已保存的历史运行工件，不能冒充当前工作区新跑出的成绩。高 faithfulness 只表明相对检索上下文的一致性评分较高，不能解释为 96% 医学正确率。Correctness 衡量参考答案关键事实覆盖与准确性，并非经临床验证的正确率。

检索脚本 `scripts/08_eval_retrieval.py:267` 用“是否至少命中一个标准 chunk”计算名为 Recall@K 的字段。多证据问题中，这应清楚标为 **Hit@K / 任一证据命中率**。本轮从 `retrieval_eval_v2_gpu.json` 原始排名重算：

| 检索方案 | Hit@5（原字段 Recall@5） | 每题证据召回率再取平均 @5 | MRR@20 |
|---|---:|---:|---:|
| P1 dense | 0.50 | 0.2667 | 0.3547 |
| P2 hybrid | 0.60 | 0.2933 | 0.4177 |
| P3 rerank | 0.70 | 0.3250 | 0.5134 |

这些数据支持“本次评估中混合检索和重排改善命中与排序”的结论，但还不能证明 Agent 自检相对同条件普通 RAG 的净收益。不同题集上的 P3/P4 成绩不能直接比较。

补足项：统一主结果表；保留历史结果但标明版本；记录 commit、语料与题集 hash、模型、裁判、prompt、硬件、错误数、分母、耗时。当前 judge 字段是 `mimo-v2.5-pro`，属于与系统检查模型相同的模型家族，应披露评估独立性限制。正式展示前用冻结条件比较普通 RAG 与 Agent，并挑选失败案例人工复核。

当前 50 题中 22 题为 Radiology、12 题为 Neurology，不宜宣传为广泛医学能力评测。strict 成功题历史耗时：均值约 22.04 秒、中位数 17.09 秒、nearest-rank P95 53.88 秒；这些是端到端历史耗时，不能与检索耗时混用。

### P0-B：默认 Docker 路径存在确定的配置矛盾

1. `docker-compose.yml:20` 固定 Qdrant `v1.9.2`，`retrieval/hybrid.py:65` 使用 `query_points`。官方说明 Query API 从 v1.10.0 提供，需要选择并验证兼容的服务端/客户端组合。[Qdrant 官方说明](https://qdrant.tech/documentation/search/hybrid-queries/)
2. `docker-compose.yml:70` 将 `/app/data` 挂载为只读；`agent/graph.py:69` 起默认向 `data/checkpoints/agent.db` 建库/写入。需要独立可写 checkpoint 存储，并与只读语料分离。
3. Compose 设置 `OLLAMA_HOST=http://ollama:11434`，`agent/llms.py:78` 却硬编码 `127.0.0.1:11434`。在后端容器内，该地址不能访问独立 Ollama 容器。
4. `--profile ollama` 只启动额外服务，未自动将后端 `LLM_BACKEND` 改成 `ollama`；注释所称一条命令切换本地模型并不完整。
5. 新 Qdrant volume 本身没有语料，启动服务不等于已经可以问答。必须补充小样本初始化步骤和空索引提示。

以上为源码与配置确认的问题；本轮未声称实际完成 Docker 构建或复现了每个容器错误。

### P0-C：质量门禁未闭合

三项测试失败的原因：旧测试仍假设默认阈值 0.6、MAX_REGEN=1，以及已移除的 `REGEN_CONFIDENCE_SKIP`。当前实现为按问题类型选择阈值、MAX_REGEN=2、无置信度绕过自检。应保留当前设计意图并更新测试契约，不能为了变绿恢复已移除的绕过逻辑。

`nodes.py:498` 的 `__all__` 仍导出已不存在的 `REGEN_CONFIDENCE_SKIP`，需清除残留。部分 E402 与已记录的 Windows 导入顺序有关，应有针对性解释或豁免，避免机械重排后破坏兼容性。

真正仓库根目录是 `medrag-agent/`，未跟踪 `.github/workflows`；父目录的空 `.github/workflows` 不构成此仓库的 CI。需在仓库内建立无需 API key 的单测、代码检查和前端构建。真实服务集成测试单独标记、显式启用；当前 README 的 `pytest tests/` 会包含依赖真实服务的测试。

Python 依赖基本只有下限，没有可复现锁定文件。README 的 Node >=18 与当前 Vite 包声明的 `^20.19.0 || >=22.12.0` 不一致。还需统一包版本 0.1.0、API 1.0.0、前端 0.0.0 的发布语义。

### P0-D：页面承诺与后端行为需一致

- **问答 P2/P3 开关无效**：`api/routes/ask.py:157` 只记录请求 pipeline，随后始终进入相同且包含 rerank 的图。本轮替身 WebSocket 探针验证了这一点。建议首版问答固定完整 Agent，隐藏该开关；Explorer 的检索对比可保留。
- **节点开始事件发送过晚**：`ask.py:173` 在拿到节点输出之后才连续发 start/end，不能准确呈现该节点的真实运行中状态。需要从执行入口/事件机制产生 start。
- **错误和超时处理未形成清晰终态**：队列超时只是 break；错误后仍可能发送 done；发送异常被 `_send_safe` 吞掉。应以故障注入验证“失败不展示成功结果、断开后任务有明确处理”。取消 asyncio 包装任务也不等于同步工作线程已停止。
- **健康检查存在假阳性**：`corpus.py:86` 把 HTTP 401 也标为 LLM connected；总体始终返回 status=ok，且没有按 Ollama 后端检查。应区分进程存活、依赖可达、认证可用与可处理请求。

## 4. 首版收敛建议

### 推荐：研究展示版 v0.1.0

保留：文献检索、固定完整问答链路、答案引用与原文定位、证据自检标签、三个代表性演示问题、小样本可复现语料、单一主评估报告。MCP 作为有文档的附加入口。

收起或明确延后：`search_visual`、图像/多模态、HyDE/Multi-query 作为主体验、多用户平台、长对话记忆宣传。历史记录可保留为“历史查看”，因为当前生成节点未消费 history/summary。修复完整上下文问答属于后续独立能力。

`quick_demo.py` 的 P4 指 HyDE，而 Agent 评估中的 P4 指 agentic，命名也需统一，避免访客误认相同实验。

### 展示材料

- README 第一屏：一句问题定义、一张实际界面截图或 GIF、三个已完成能力、准确主结果表、快速体验入口。
- 60–90 秒演示：正常回答 → 点开引用与证据 → 证据不足案例。另给重写/自检案例，明确哪些是真实录制、哪些是样例回放。
- 提供小型、来源和使用边界清楚的文献样本及确定性初始化命令。大语料重建作为高级路径；冷启动模型下载大小、内存/显存和耗时用实测记录。
- 优先保证本地真实演示；可增加无需 key 的静态录制回放，必须明确标注回放。公开视频/截图能满足首版展示，不必强行开放公网付费问答服务。
- README 加载模型和平台说明应与真实测试一致；Windows、Linux、macOS 未测路径明确标注。

### 安全和发布边界

MCP 的鉴权/限流不能等同于 Web API 的保护。目前 API 路由没有相同的认证与会话所有权校验；读取历史只依赖 thread_id。首版本地展示可采用回环绑定；若未来开放公网真实问答，需单独完成身份、会话隔离、访问限额和费用控制验收。

已有 LICENSE 和忽略规则是基础，但没有完成历史密钥检查。发布前检查 Git 历史与候选工件，排除密钥、运行日志、私人问答和数据库；数据样本应单独记录来源及许可信息，不能把代码许可证视为全文数据授权。
