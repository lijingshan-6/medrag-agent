# VeritasMed v0.4 实施计划：逐项回答，逐项对应证据

制定日期：2026-09-22。状态：候选版实现与交付完成，效果目标未达成；真实运行记录见 [实施记录](../../agent-v0.4-worklog.md)。

基线是已推送的 [`v0.3.0`](https://github.com/lijingshan-6/medrag-agent/tree/v0.3.0)
（`ee9837a`）。本地实现版本为 0.4.0 候选版；v0.3 标签与结果不变，未达成的效果目标继续保留。

## 1. 最终要交付什么

v0.4 要让读者从答案中看清：**问题的各个部分分别由哪篇研究、哪段原文支持，
哪些部分当前证据回答不了。** 重点是回答效果和可演示性。

一次完整的 Live Ask 应当做到：

1. 保留原始问题，列出实际需要回答的要点及其研究范围。
2. 给每个要点找到对应原文，保留必要的人群、比较对象、数字和结论边界。
3. 根据这些证据生成有引用的答案；多研究问题分别呈现各研究结果。
4. 对未获得证据的部分明确说明缺口，不用邻近研究或合理猜测补成结论。
5. 界面展示“当前证据足够 / 部分足够 / 不足”的状态，以及可点开的相关段落。

例如，用户同时询问研究的诊断表现和实际临床获益：有诊断数据时回答诊断表现；
没有临床结局证据时明确缺口，不推断“已经改善患者结局”，也不编造拒答理由。
状态描述的是本次检索到的证据是否覆盖问题，不代表医学正确率或临床认可。

最终交付包括实现代码、真实问答示例、逐题结果报告、界面演示和可照做的 README。
保留现有 LangGraph、Ollama `qwen3.5:9b`、BGE-M3 和重排方案。

## 2. 为什么现在做这一版

v0.3 的 15 道开发题已经为 13 道可回答题找齐必要证据，但严格通过只有 10/15。
因此这一轮先解决“证据已经找到，却没有完整、准确地写进答案”的问题。

| 当前表现 | v0.3 实测 | 对 v0.4 的含义 |
|---|---:|---|
| 找齐必要证据 | 13/13 道可回答题 | 保留已有检索能力，先改答案组织 |
| 严格通过 | 10/15 | 还需要保留细节、来源范围和证据边界 |
| 遗漏必要限定条件 | 共 5 处 | 生成前显式记录这些条件 |
| 无依据或范围错误的额外陈述 | 共 2 处 | 答案每个实质性补充都需有对应证据 |
| 自检判通过 | 14/15 | 自检漏掉全部 5 道严格失败，不能充当评测分数 |
| 平均端到端耗时 | 91.3 秒 | 记录新增步骤的代价，减少不必要的整段重写 |

以上来自一次完整开发集运行，不能视为未见题表现或重复运行稳定性。
依据见 [v0.3 报告](../../agent-v0.3-report.md) 和
[全部真实答案及证据](../../agent-v0.3-cases.md)。

## 3. 核心改法：先做有来源的回答提纲

在现有问题分解与证据筛选之间建立清晰的逐项对应关系，并在生成前完成提纲。
生成与检查使用同一份提纲，而不是各自重新猜测问题需要什么。

每个回答要点至少记录以下内容，具体字段在第一步实现时确定：

| 内容 | 用途 |
|---|---|
| 原始问题中的要点 | 防止查询改写后丢失用户的真实问题 |
| 要求的研究范围与实际匹配的来源 | 区分同一研究、多篇研究和无法确定来源的情况 |
| 原文片段、chunk ID 和引用 ID | 让提纲中的事实可以回到实际检索文本 |
| 必要限定条件 | 按问题和原文记录人群、比较对象、时间、效应量及必要的不确定性 |
| 要点状态与证据缺口 | 标记有支持、只有部分支持或没有足够支持 |
| 对应答案内容 | 便于定位遗漏和修复，不让引用只挂在整段结尾 |

提纲由用户问题和实际检索证据产生，不能从黄金题集读取限定条件。
不要求每句话罗列全部统计量；只保留影响该问题含义、比较和结论的必要信息。

程序可以确认引用存在、原文片段确实来自该 chunk、来源标识一致。
语义上是否足以支持结论仍需要模型检查和离线对照原文的评阅；格式正确不等于结论正确。

来源选择遵守这些规则：

- 同一研究的多个要点允许使用同一来源的多个片段，不强迫每个要点换一篇文章。
- 点名研究时确认来源与问题匹配，不能直接把排序第一的文章认定为目标研究。
- 多研究问题分别保留各自结论及比较条件，不能自行生成没有依据的汇总结论。
- 所需细节已经存在于候选片段时优先保留它，不因主题相近或统计数字更多而替换掉。
- 当前材料不足时保留缺口。“未在当前证据中找到”不等于“所有文献均不存在”。

## 5. 怎么判断这一版有没有真正变好

### 开发期间

保持 v1.1 的 50 道题及评分规则不变，继续只使用 15 道开发题。
不通过重写标准答案或降低限定条件要求来提高分数。

先围绕上述五道失败题迭代，并保留 VMG-024 这个自检误判案例。
实现稳定后，在同一代码和模型配置下，将这六题各独立运行两次，保留全部输出，
观察遗漏和额外陈述是否反复出现。随后另做一次完整的 15 题运行作为正式开发结果；
不能挑各轮最好的答案拼成一份报告。

按已有口径逐题对照冻结原文评阅，额外关注黄金主张之外的新陈述和跨来源归属。
自检结果只用于分析；自动计算负责重算已经明确记录的评分决定。
报告如实说明评阅来源，不把模型或工程评阅称为独立临床专家审查。

### v0.4 开发目标

| 项目 | 目标 |
|---|---|
| 严格通过 | 完整开发运行至少 13/15 |
| 无依据或范围错误的额外实质性陈述 | 完整开发运行和上述重复案例均为 0 |
| 找齐必要证据 | 保持 13/13 道可回答题 |
| 缺失证据的处理 | 部分可回答与不可回答题均明确边界，不编造理由 |
| 已有成功案例 | 逐项说明是否保持通过，不以总分掩盖退步 |
| 运行表现 | 公布平均耗时、最慢案例和修复次数，不为提速删掉关键证据 |

13/15 是本轮开发目标，不是对未来结果的保证。重复案例只提供有限的稳定性观察，
不能据此宣称广泛可靠。若目标未达到，记录实际结果并保持候选状态，不降低评分要求。
即使满足目标，也只说明这个冻结快照上的工程效果，不构成临床验证。

### 首次使用 35 道测试题的条件

等开发目标达成、实现与评分口径固定后，再做一次完整测试集运行。
在此之前，不查看测试题的逐题表现来指导提示词、检索或答案生成改动。
首次测试结果与开发结果分开报告；即使出现失败也完整保留，不能回填优化后的答案。

一旦使用测试结果指导后续改动，这一集合对后续版本便不再是未见测试集，
需要明确这一事实，再为后续泛化主张准备新的独立题目。
本轮已完成上述开发推理协议；开发目标未达成，因此没有执行 35 道测试题。

## 6. 范围与交付清单

这一版围绕回答效果、来源展示和上手体验收敛。暂不扩充题集数量，不引入新模型组合，
不增加多用户部署、权限平台、并发压测或复杂评测服务。
自动化用例只覆盖此次易错的事实行为：来源错配、比较对象遗漏、边界丢失和错误修复。
实际问答、引用能点开、示例能运行，以及 README 可照做，是展示交付的重点。

## 7. 本轮结果与后续入口

实现、演示和文档作为候选版本收齐，回答效果不满足进入测试集的条件。
完整开发集严格通过 **9/15**，找齐必要证据 **12/13**，存在 **3** 处
无依据或范围错误的补充、**2** 处必要限定条件遗漏及 **1** 道执行失败。
六题重复运行分别通过 5/6 和 4/6，其中第二轮有一道执行失败。

详见[结果报告](../../agent-v0.4-report.md)。第五步交付完成不代表第二、三步尚未勾选的
质量要求已经完成；它们继续作为待修问题。先修复研究内样本角色和拒答理由、保留必需对照
与第二来源，再解决边界提纲的无效结构化输出。之后重新固定实现，按相同开发协议评阅。

v0.3 标签、50 道黄金题和评分规则均保持不变。35 道测试题的条件未满足，继续不运行。
候选版保存在 `feature/veritasmed-agent-v0.4`；本轮没有创建稳定 v0.4 标签或推送 GitHub。
