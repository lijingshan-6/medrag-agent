# v0.4 实施记录

状态：开发中。当前公开基线仍是 v0.3；尚未声明 v0.4 达到效果目标。

## 已实现的路径

- 问题要点、来源片段、必要限定条件和缺口保存在同一个回答提纲中。
- 对点名研究和多研究问题，先匹配研究身份，再构建提纲；不直接认定排名第一的文章就是目标。
- 模型选择程序编号的原文句段；程序取回原文并核对来源，不依赖模型逐字复述。
- 每条生成陈述携带要点编号，不能引用该要点之外的来源。
- 检查返回具体需修复的要点，并可纠正将邻近结果误当成所问结果的提纲判断。
- 修复保留其他要点已有的回答；核对提纲中必需的数字是否遗漏。
- API 和界面提供证据覆盖状态、缺口、逐项展开的原文与来源定位。
- Guided 示例覆盖完整、部分、证据不足；继续标明固定示例，移除模型置信度百分比。

## 开发中发现的问题

1. 第一轮模型漏写要点编号，来源绑定拒绝了这些陈述；补齐 JSON 示例。
2. 第二轮发现引用被模型改写后无法逐字匹配，也观察到样本量遗漏；改用原文编号选择，
   单独提取研究人群，并核对必要数值。
3. 第三轮发现同主题的另一篇研究混入了单研究问题的证据缺口；增加生成提纲前的研究身份选择，
   后续步骤只读取被选中的来源。
4. 后续探针发现“答案漏写”被自检误当成“原文无证据”；区分答案完整性与来源支持，
   不再因漏写而直接把有证据的要点变为拒答。最后一次检查否定的推断也会从可见答案移除。
5. 对仍然漏写的已绑定数值，直接补充带来源的完整原文句子，再交给自检，
   不为抄回已有数字额外调用模型，也不自行推导新结论。明确写出入组人数的原句
   由程序一并保留，避免模型的研究人群字段为空时再次遗漏样本量。
6. 直接输出模式仍会将诊断指标误当成下游临床获益。推理模式的小试正确区分了两者；
   第六轮的温度 0 推理耗尽输出预算仍未给出答案，已中止，没有完整题目输出。
   第七轮改用温度 1.0 仍出现截断；第八轮扩大到 16384 上下文和 8192 输出预算，
   模型部分卸载到 CPU，推理速度由约 40 降至约 23 token/s。均在首题完成前中止。
   第九轮将推理限定在“研究是否证明某个结果”的提纲判断，普通提取和复核使用直接输出。
   推理温度参考 [Qwen 官方模型卡](https://huggingface.co/Qwen/Qwen3.5-9B#best-practices)，
   本机 Ollama 模型的默认值也是 1.0；统一为 8192 上下文、最多 4096 输出 token。
   技术性无效输出会报告执行失败，不当作医学证据不足。完整答案效果仍在观察中。
7. 第九轮完成六题，双研究来源与比较值得到保留；仍观察到样本量遗漏、缺口不能被修复，
   以及边界判断的无效输出重试。随后加入原文人群补全、可单独修复的缺口和更简短的
   结局判断提纲；支持部分与缺失部分可同时返回，避免一项缺失就整题拒答。

Windows 本地 CUDA 环境还遇到模型加载时的原生崩溃；显式先加载 Arrow、再加载 ML
运行时，并隔离用户级 Python 包后，后续开发运行完成。演示安装使用依赖锁中的独立 CPU
环境，不要求读者复用这台机器的 Conda 环境。

这些都是开发探针，不能作为最终版本分数。探针保留在本地 `.benchmark-runtime/v04_probe*_raw.json`；
已中止的轮次只包含中止前完成的题目。最终结果将来自固定实现上的独立完整运行。
